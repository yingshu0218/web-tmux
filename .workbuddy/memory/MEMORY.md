# tmux-web 项目长期约定

## 工具与产出

- **产物归档在 `.workbuddy/artifacts/<日期>-<主题>/`**，每个目录自带 `README.md` 与原始日志，
  保证「换个会话也能看懂并复跑」。不要只把结论写在聊天里。
- **浏览器侧性能/功耗量化**：`.workbuddy/artifacts/2026-09-30-浏览器开销诊断/browser-load-probe.mjs`
  （零依赖 CDP）。用法 `node browser-load-probe.mjs`（全场景）/ `MODE=ab node browser-load-probe.mjs`
  （只跑动画 A/B 归因）。**改过 CSS 动画 / 渲染路径 / 输出协议后应复跑一次**；
  分场景判据与基线表写在 `AGENTS.md` 的「性能红线」小节。

## 浏览器开销基线（2026-09-30 修复前 → 修复后，测试站 1 台机 / 2 会话）

| 场景 | 修复前 主线程 / 样式重算 | 修复后 |
|---|---|---|
| 会话总览页 | 4.7% / 60.0/s | **0.4% / 3.0/s** |
| 终端页 · 未开会话 | 4.4% / 60.1/s | **0.3% / 2.5/s** |
| 终端页 · 1 个空闲终端 | 6.6% / 60.0/s | **0.9% / 7.8/s** |
| 终端页 · 高速输出 | 8.0% / 69.8/s | **2.1% / 17.6/s** |

- **`样式重算 = 60/s`（等于刷新率）是「有不可合成的无限动画在跑」的指纹**，
  发现这个数字就去看 `styles.css` 里 `animation: … infinite` 那几条。
  修好后应掉到**个位数**（不是 0）。
- **已修**：`styles.css:380` `.dot.online` 原先动画 `box-shadow`（不可合成）→ 每帧重算样式 + 重绘，
  占「终端页未开会话」场景空载 CPU 的 **95%**（4.1% → 0.2%），并让页面永不空闲。
  现改为在 `::after` 上动画 `transform: scale(2.75)` + `opacity`。
  残留仍有约 3~18/s（软件合成环境下 Chrome 会周期性回主线程），
  且**随状态点数量次线性增长**（4 个点 0.45%、64 个点 1.56%）——可接受，但几十台服务器时要复查。
- **xterm 已换成 WebGL 渲染器**（`@xterm/addon-webgl`，纯 JS 无原生编译），带
  `onContextLoss` 回退与卸载 `dispose()`（原先**完全没有 dispose**，等于每开关一次标签泄漏一个实例）。
  判据：`canvas > 0` ⇒ WebGL；**不要看 `.xterm-rows > div`**（用 WebGL 后它恒为 0）。
- **终端输出协议已改**（`server/src/ws.js`）：`?bin=1` 协商走「~16ms 合并 + 二进制帧」，
  不带参数的老前端仍拿 base64 文本帧。实测 1MB 输出只产生 **10 条帧**（原先上千条小消息）。
  这是全仓库**唯一被授权的 `server/` 例外**，改之前先读 `AGENTS.md` 性能红线第 ③ 条。
- **已实测否定的假设**：`.rail` / `.statusbar` 的 `backdrop-filter` **与主线程开销无关**
  （去掉/恢复：6.1 → 6.1 → 6.1，完全无变化）。不要在无实测支撑下动它。
- **测量边界**：`Performance.getMetrics` 只覆盖渲染进程主线程；
  GPU / 合成器 / `WindowServer` **无头环境测不到**，必须在真机上用
  Chrome 任务管理器 + 活动监视器另行复核。

## 用 CDP 打远程测试站的固定坑（别再踩）

1. Chrome 启动**必须带 `--no-sandbox`**（还要 `--disable-gpu-sandbox --disable-dev-shm-usage`）。
   否则沙箱里 Chrome 自己的 sandbox 起不来 → `GPU process isn't usable. Goodbye.` + SIGTRAP，
   表现成「CDP 刚连上就断 / 命令超时」，极易误诊为 CDP 用法写错。
2. 用页面内 `fetch('/api/login')` 登录后**必须 `Page.reload()`**。
   Cookie 拿到了不等于应用知道：`App.tsx:202` + `useEffect(checkAuth)` 只在**挂载时**读一次登录态，
   不重载就永远停在登录页 —— 后面每个「场景」其实都在测同一个登录页。**为此白跑过一整轮测量。**
3. 探针自己的环境变量**别用 `USER`**（被 shell 占用，macOS 上是系统用户名）→ 登录静默 401。
   一律加前缀，如 `TW_USER` / `TW_PASS`。
4. 连接后先做 **rAF 自检**（`requestAnimationFrame` 帧率，实测 61 fps）。
   rAF 不触发时 xterm 根本不会渲染，会测到一片 0% 并得出完全相反的结论。
5. **证据纪律**：一次性调试脚本得出的数字**必须同时归档原始日志**。
   本仓库犯过一次：报告里写「xterm 空闲只占 0.13%」，而归档日志里同场景实测是 2.7%（且仍有 60/s），
   被独立审计抓出来 —— 该结论已作废并重测归因。

## 性能改动的固定交付节奏

先量化定位 → 出方案 → 用户拍板 → 一次改完 → 本地 `tsc -b` / `build` / `node --check` / 两个自检脚本
→ 源码部署测试站 → **用探针复测并留档** → 派独立子 agent 只读审计 → 处置审计意见 → 汇报。
审计发现的问题要**逐条给处置结论**（修 / 不改 + 理由），不要只贴审计原文。
