### 落地策略：为什么这次改动这么小

通读 `styles.css`（904 行）后发现：**上一轮出的设计稿本身就是照着现有 DOM 结构画的**，
`styles.css` 里的类名和 JSX 结构（`.sess-head/.sess-meta/.sess-preview/.sess-foot`、
`.rail-node`、`.compose`、`.login-stage`、`.cfg-card`）和稿子几乎一一对应。

所以落地是 **~90% 样式层重写 + ~10% 展示层调整**，而不是重构 JSX。
这条经验值得记：**先读代码再出稿，落地成本会低一个数量级**；
反过来先自由画稿再改代码，往往要重写 JSX。

### 关键实现点（也都是坑）

1. **`backdrop-filter` 只能给「不含 fixed 后代」的容器。**
   `.rail` / `.statusbar` / `.login-card` 可以；`.app` **绝对不行** ——
   它会给 `.drawer` / `.modal` / `.cmdk` 造出新的包含块，
   让 `position:fixed` 变成相对 `.app` 定位。环境光晕改用纯 CSS
   `radial-gradient` 叠在 `.app` 的 `background` 上，不引入图片、不新增节点。
2. **玻璃只给三处**（rail / 状态条 / 登录卡）；内容卡一律走半透明提升面
   `rgba(255,255,255,.045)` + `1px rgba(255,255,255,.07)` + 柔阴影。
   给内容卡加 `backdrop-filter` 会把终端预览文字糊掉。
3. **圆角档位建立为令牌**（`--r-xs` 6 / `--r-sm` 8 / `--r` 10 / `--r-lg` 14 / `--r-xl` 18 / `--r-2xl` 22），
   旧的 4/6/8 硬编码全部替换。写进 AGENTS.md §5.3 作为硬约束。
4. **JSX 里不能把 `{/* 注释 */}` 放在 `{cond && (` 之后的表达式位置** ——
   那是 JS 表达式位置，会报 `TS1005 ')' expected`。注释要放进 JSX 元素的 children 里。
5. **页头层级靠 `margin-right:auto`**，不靠加边框：
   `.ov-search { margin-right: auto }` 把右侧的视图切换 / 刷新 / 主操作推到行尾。

### 先纠正第二轮的一个错误结论

第二轮写的是「自托管只有 Inter 400/500/600 + JetBrains Mono 400/500」——
**这是错的，把「声明」当成了「有字形」**。
实际：fonts.css 共 12 条 @font-face，src **全部指向仅有的 4 个 400 字重文件**，
即除 400 外的每一个字重都是浏览器合成加粗（faux bold），比当初描述的更严重。
教训：判断字体是否可用不能数 @font-face 声明，要看有没有独立字形文件，
或直接看 FontFace 的 weight 是不是区间。

### 做法：可变字体（比补 4~6 个静态字重更省）

从 @fontsource-variable（jsDelivr）取 4 个文件替换原来的 4 个静态 400 文件：

| 文件 | 大小 | 覆盖字重 |
| --- | --- | --- |
| inter-latin-var.woff2 | 48256 | 100-900 |
| inter-latin-ext-var.woff2 | 85068 | 100-900 |
| jetbrains-mono-latin-var.woff2 | 40404 | 100-800 |
| jetbrains-mono-latin-ext-var.woff2 | 15196 | 100-800 |

总体积只比原来多 **12KB**（176.6K → 188.9K），却拿回全部真实字重
（Inter 可变字体甚至比它的静态 400 还小）。
fonts.css 从 12 条声明收敛成 4 条，font-weight 写成区间。
保留原 font-family 名，unicode-range 与旧版逐字一致（已验证）。
format 写 woff2 而非 woff2-variations（兼容性更稳；可变轴只看 weight 是否区间）。

### 只读模式视觉锁定（接上 .term-locked）

原先全项目零引用的 `.term-locked` 已接上，但**没有沿用它的原规则** ——
`filter: grayscale(.9) brightness(.6); pointer-events: none` 会把滚动、复制、

挂载点是 `TermPane` 自己的根节点（不是 `.term-panes` 容器）——
终端是**每个 tab 一个 pane**，锁定状态必须按 tab 独立。

## 第十轮：终端工作区支持单屏 / 双屏 / 四分屏（同日）

用户要求「会话页面要支持单屏、双屏、4分屏」。经确认：加在**终端工作区**，
且**每个格子可独立挑会话**（不是按顺序铺开已打开的标签）。

### 架构：tabs 与 slots 分成两层

| 层 | 是什么 | 生命周期 |
| --- | --- | --- |
| `tabs` | 已打开的终端连接池（各握一条 WebSocket） | 只有 closeTab 才销毁 |
| `slots` | 长度 = 格子数，每格一个 tab key | 随布局增删 |

**渲染仍走 `tabs.map`**，靠 grid 的 `order` 落位、不在 slots 里的置 `display:none`
—— **隐藏但不卸载**。若图省事改成 `slots.map`，切出视野的终端会断连丢 scrollback。

### 几个关键实现点

1. **`active` 拆成 `visible` + `active`**：visible 决定是否 fit，active 只决定 focus 与描边。
2. **尺寸自适应改 `ResizeObserver`**（原来只在 active 变化 / 窗口 resize 时 fit，
   而分屏切换、rail 折叠都会改尺寸）。**必须跳过过小的尺寸** ——
   否则 `display:none` 的元素会按 0 宽算出 0 列，还会把这个尺寸发给 tmux 把远端窗口带坏。
3. **激活格用 `outline` 而非 `inset box-shadow`** —— 后者画在内容之下，会被终端 canvas 盖住。
4. 只读角标要保持正确的定位基准：`.term-pane` 加了 `position: relative`
   （否则它会以 `.term-slot` 为基准跑到格子头上面去）。
5. 窄屏（≤900px）双屏改上下排列。

### 查出并修掉的一个 bug

## 第十五轮：排查「重连是否必须重放一遍历史」

用户问：「tmux 会话从一个客户端重连进去以后，一定要逐条加载一次所有的历史记录吗？」

### 结论：不是 tmux 在重放历史

用 pty over ssh 直接量字节（`pty.fork` + `TIOCSWINSZ` + `ssh -tt`）：

- 造一个 **267 行历史**、可见区 34 行的会话，attach 收到 **1.5–1.9 KB**（≈ 一屏 32 行），
  **历史一行都没发**（判据：收到的字节里有没有 `HISTLINE-1` → `False`）
- 同尺寸 / 改尺寸 / 再回原尺寸，三次都是 ~一屏
- attach 到运行彩色 TUI 的真实会话 ≈ **19 KB** —— 仍是一屏
  （213x32 ≈ 6.8k 单元格，带 SGR ≈ 2.8 字节/格）

**tmux 是屏幕渲染器**：只发"屏幕状态"，不转发中间的滚动输出。
所以哪怕 pane 里的程序重画 80 行，客户端也只收到最终那一屏
（用模拟 TUI 实测：重画 80 行 → 收到仍是 1.5–2 KB）。

### 真正让人看到「重画一遍」的四个原因

| # | 原因 | 实测证据 |
| --- | --- | --- |
| 1 | `window-size=latest`（全局默认）→ **最新 attach 的客户端尺寸说了算** | 控制台 attach 把会话从 `213x33` 改成浏览器尺寸 `151x31` |
| 2 | 尺寸一变 → pane 内进程收 SIGWINCH → agent 类 TUI 重排重画 | 他们的会话跑的是 `node`（agent TUI） |

## 第十七轮：会话卡片「⋯」菜单被视口底边裁掉（交互修复）

用户截图：会话总览右下角卡片点开「⋯」后，「会话管理…」「终止会话」被切在视口外看不到。

### 根因：定位逻辑用**写死的高度上限**猜菜单尺寸

```jsx
// 旧实现（Overview.tsx ContextMenu）
style={{ left: Math.min(st.x, innerWidth - 190), top: Math.min(st.y, innerHeight - 220) }}
```

`innerHeight - 220` 是按「菜单不超过 220px」估的。**实测该菜单高度 235px** ——
所以它只会硬贴底、必然溢出 15px 以上；再加上它**没有"放不下就向上翻"的逻辑**，
窗口越矮裁掉越多，用户直接看不到危险操作项。

### 修法：实测尺寸 + 双向翻转

`useLayoutEffect` 里读 `getBoundingClientRect()`，然后：

1. 右放不下 → 翻到左侧；两侧都不够 → 贴右缘 / 贴左缘
2. 下放不下 → **翻到点击点上方**；上下都不够 → 贴边
3. 极端情况（菜单比视口还高）→ `max-height: calc(100vh - 16px)` + 内部滚动，不再被裁

用 `useLayoutEffect` 是刻意的：它在浏览器**绘制前**同步跑，所以不会看到菜单先出现在错误位置再跳一下。
未测量前先 `visibility: hidden`，保证连一帧都不闪。

顺手补的交互细节：
- `Esc` 关闭（原来只能点外部关闭）
- `role="menu"` / `role="menuitem"`（无障碍语义）
- 菜单项 `white-space: nowrap`（避免收窄时标签折成两行）
- `overscroll-behavior: contain`（极端滚动时不带动页面）

> 刻意**没做**键盘上下选择 + 自动聚焦：终端页共用同一个组件，
> 自动聚焦会把焦点从 xterm 抢走，用户打完菜单还得点回终端 —— 反而更差。
