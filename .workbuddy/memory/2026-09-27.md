### 问题 1 + 2 是**同一个 bug**：无 body 的请求带 `Content-Type: application/json` → Fastify 400

**用户描述**：添加凭据时提示 bad request，但服务器实际已添加成功；添加失败的服务器也在列表里，
且删除时同样报 bad request 删不掉。

**根因**（实测复现）：

```
$ curl -X POST .../api/servers/1/check -H 'Content-Type: application/json'   # 无 body
{"statusCode":400,"code":"FST_ERR_CTP_EMPTY_JSON_BODY","error":"Bad Request",
 "message":"Body cannot be empty when content-type is set to 'application/json'"}
$ curl -X POST .../api/servers/1/check                                        # 不带该头
{"items":[...]}   # 200
```

前端 `req()` 无条件加 `Content-Type: application/json`，于是**所有无 body 的 POST/DELETE 全废**：

| 接口 | 用户可见表现 |
| --- | --- |
| `POST /api/servers/:id/check` | 添加向导报错、卡在第 2 步（**用户报的**） |
| `DELETE /api/servers/:id` | 删除服务器删不掉（**用户报的**） |
| `DELETE /api/servers/:id/sessions/:name` | 终止会话失效 |
| `POST /api/servers/:id/fix-linger` | 一键修复失效 |
| `POST /api/servers/:id/push-tmux-conf` | 一键下发配置失效 |
| `POST /api/logout` | 退出登录失效 |

**为什么"报错了却已经添加成功"**：向导顺序是先 `addServer`（入库成功）再 `checkServer`（400），
用户看到失败提示，但记录已经在库里了 —— 这也是列表里出现"添加失败的服务器"的原因。

**修复两层**：
1. **前端 `api.ts`**：`req()` 只在 `opts.body != null` 时才加 JSON 头（根因）
2. **后端 `index.js`**：`removeContentTypeParser` + 自定义 `parseAs:'string'` parser，
   空 body → `done(null, {})`；**但非法 JSON 仍抛 400**（不能把解析失败也吞掉）
   —— 兜住浏览器里缓存的旧前端
3. 附带：`req()` 错误文案改为 `message || error || HTTP <status>`。
   Fastify 内置错误体的 `error` 恒为 `"Bad Request"`，只看它用户永远只能看到一句废话

**另外改了向导的容错**（`Servers.tsx` 的 `toStep3`）：把「入库」与「接入检查」拆成两段 ——
只有入库失败才算添加失败；入库成功之后无论检查结果如何都进第 3 步，
并在底部写明「该服务器已保存到列表。接入检查未通过不影响保存…」。
就是为了不再出现「提示失败但其实已入库」这种认知错位。

**后端验证**（4 条断言全对）：

| 用例 | 结果 |
| --- | --- |
| 空 body + JSON 头 POST `/check` | 200（修复前 400）✓ |
| 空 body + JSON 头 DELETE 不存在目标 | 404（业务逻辑到达了）✓ |
| 非法 JSON | 400（没有被兜底吞成 `{}`）✓ |
| 空对象 `{}` → 业务校验 | 400「名称不合法」✓ |

**浏览器端到端**（CDP 全绿）：走完向导 → step3 出现且显示 `✕ connect ECONNREFUSED 127.0.0.1:1`
→ 保存 → 列表从 1 行变 2 行 → 点删除 → 确认框 → 删除成功 → 列表回 1 行；页面错误 `[]`。

### 问题 4：回车要和文本**分两次**送达

**用户描述**：在发送框输入后按回车，文本进了 tmux 里的对话框但没提交，还得再按一次回车。

**根因**：AI CLI（用户 `work` 会话里跑的正是这类 TUI —— 实测 `bypass permissions (shift+Tab to cycle)`、
19.2M tokens）会把**同一批到达的连续字符 + 换行**识别成一次粘贴，
于是那个 `\r` 只当作粘贴内容里的换行，**不触发提交**。
原实现是 `sendGuarded(draft + '\r')` —— 一个字符串一次写下去。

**修复**（`Terminal.tsx`）：
```ts
send(text);                                        // 文本
window.setTimeout(() => send('\r'), ENTER_GAP_MS); // 回车单独一帧，间隔 80ms
```
**关键坑**：拆分后两次发送若都调 `sendGuarded`，在 copy-mode 下会**补两个 `q`**。
所以要先算一次 `needExitHistory`，补完 `q` 之后走裸 `send`。

**端到端证据（两段）**：

1. 浏览器发出的 WS 帧（CDP `Network.webSocketFrameSent`）：
   `{"t":"i","d":"hello-probe"}` 然后 `{"t":"i","d":"\r"}`，**间隔 79ms**
2. **服务端 raw 探针**（在目标会话里跑 raw-mode python 逐次 read 并记录 chunk 与时间）：
   ```
   47.162  len=11  b'hello-probe'
   47.246  len=1   b'\r'
   ```
   → 穿过 ssh pty + tmux 之后仍是**两次独立的读**，间隔 84ms。
   （如果只做第 1 段只能证明前端拆了帧；第 2 段才证明终端真的分两次收到）

**回归**：bash 会话里 `echo TW_SEND_OK_2026` + 回车正常执行（`capture-pane` 有回显与结果）。
这条必须验，否则拆帧可能把命令拆坏。

### 关键设计决策（后续落地时要沿用）

- **保留产品身份色**：电青 `#00f2fe`（主操作 / 激活 / 焦点）、翡翠绿 `#4edea3`（在线 / 活跃 / 成功）、
  琥珀 `#fbbf24`（重连中 / 非默认 socket）、红 `#f87171`（危险）。**只换表面处理，不换品牌色**
  —— 与 `styles.css` 的 `:root` 令牌一一对应，落地时可直接映射。
- **画布基底** `#070A12` + 三处径向环境光晕（电青 / 翡翠绿 / 淡蓝），光晕溢出画布由 clipsContent 裁掉。
- **玻璃只用在 rail 与顶部状态条**（`BACKGROUND_BLUR` 32–40 + 白色 0.04 填充 + 0.07 描边）。
  会话卡是**不透明提升面**（白 0.045 + 白 0.07 描边 + 圆角 18 + 柔和投影）——
  刻意不给内容卡上毛玻璃（会糊掉终端文字）。
- **圆角整体放大**：卡片 18 / 按钮与输入 10–12 / 胶囊 999（旧版是收紧的 4/6/8）。
- **字体不变**：Inter（界面）+ JetBrains Mono（终端 / 指标 / 数字）。已验证设计工具内两个字族均可用
  （注意：Inter 的半粗在工具里叫 `SemiBold`，不是 `Semi Bold`）。
- **去掉重复标题**：旧版顶部状态条与页面内容区各有一个「会话总览」。新版**状态条只放全局控件**
  （快速检索 + 集群状态 + 账号），**页面标题留在内容区**并配一行摘要。
- **会话网格 2 列**（1144px 可用宽 → 每张 565px）。这与现有
  `repeat(auto-fill, minmax(392px,1fr))` 在该宽度下的实际表现一致，不是随意改的列数。
- **卡片信息编排重做**：名称行（会话名 + 标签组）+ 状态徽标 → 一行元信息（路径 · 窗口 · 客户端）
  → 终端预览 → 操作区（进入工作区 / 只读 / 独占 / ⋯）。
- **筛选项在 rail 回显**：工具栏的节点筛选 chip 必须有对应的 rail 节点高亮（青色底 + 青描边），
  否则出现「页面说在筛选、侧栏看不出来」的割裂。

### 设计工具侧的施工经验（Ardot）

- `padding` **只可靠地用统一数值**（工具内部会展开成 `{top,right,bottom,left}`）。
  副作用：**统一 padding 会给 pill / 按钮强加纵向内边距**，
  所以带固定高度的胶囊要小心 —— 稳妥做法是**胶囊不写死高度、用小的统一 padding 让它 hug**。
- `M(nodeId, parentBinding, index)` 可用于把刚插入的子节点**挪到指定位置**
  （本次用它把「独占」按钮插到「只读」之后、弹性占位之前）。
- 校验节奏：每个分组做完跑一次 `capture_layout(problemsOnly)`；
  只有「光晕超出画布」与「rail 中部空白」两类预期警告 —— 两者都是刻意设计，不要"修"。
- 卡片类重复组件靠**逐张写 ops**（每张约 29 个节点），分 4–5 个 batch 完成；
  单批上限 25 ops，别硬塞。

### 本轮确立的设计语言（与上一轮一致，补充细则）

- **胶囊/按钮一律 hug 高度 + 小统一 padding**（胶囊 padding 6、按钮 padding 8–10）。
  写死 height 会让统一 padding 把内容压到溢出。
- **表格**：单元格必须是 frame 包 text；列宽 名称 150 / 地址 230 / 连接身份 150 / 状态 110 /
  延迟·会话 130 / 操作 fill；行高 56，行间用 1px frame 做分隔线；操作列右对齐，
  主操作有描边、次级只留文字、删除用红色文字。
- **状态色语义**（全站统一）：在线/活跃/成功 = 翡翠绿；重连中/非默认 socket/**连接身份与配置不一致** = 琥珀；
  离线/无数据 = 中性灰；破坏性操作 = 红。
- **服务器管理的「连接身份」列**是本产品的差异化信息（§5.9），必须带凭证芯片；
  `dev-box` 那行刻意做成「配置 ubuntu、实际 root」的琥珀不一致态。
- **终端工作区**不渲染全局 rail，用自带侧栏；自上而下 = 标签条 → 信息栏（身份/模式/socket/延迟/CPU/内存/磁盘/UTF-8）
  → tmux 窗口条（含滚轮模式下拉 + 历史视图提示 + 实时/只读/独占/重连）→ xterm 画布 → 发送区（头部 + 输入行 + 按键条）。
- **接入检查**从模态改为服务器管理页内的常驻面板（4 个检查项 + 状态徽标 + 一键修复/下发 + 完成）。
